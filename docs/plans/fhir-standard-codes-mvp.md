## 1. Feasibility verdict

**Yes — the MVP shared/ slice is feasible and low-risk, with six named caveats.** The architecture is sound because every mapping lives in a brand-new sidecar file (`fhir-mapping.json`) that the tool fully owns, so the round-trip invariant is automatic for XLSX/JSON-config bytes rather than at risk. Caveats:

1. **Determinism is NOT free** — `JSON.stringify(obj, null, 2)` does not sort keys and emits no trailing newline; the serializer must implement a recursive sorted-key replacer plus an explicit `\n` and be proven by an **idempotence** byte-equality test (see caveat 2 for why it is idempotence, not raw no-op).
2. **The round-trip contract is IDEMPOTENCE, not "byte-identical to arbitrary input."** A canonicalizing serializer (sorted keys + 2-space + LF + trailing `\n` + canonical JSON number/string forms) is a fixpoint only on its own output. A human- or foreign-tool-written sidecar (4-space/tab indent, CRLF, semantic key order, `\uXXXX` escapes, non-canonical number literals like `0.10`/`1e3`) is **legitimately rewritten once** on first save. The honest contract is: (a) `serialize(parse(serialize(x))) === serialize(parse(x))` for all `x` (idempotence), and (b) re-saving a file this serializer already produced is byte-identical (no-op-on-own-output). The V1 route's read-compare-before-write only suppresses spurious writes for files **already in canonical form**; the first canonicalization of a foreign file is intentional, tested, and documented (Section 3, Section 4.4, Section 4.10).
3. **The proposal's gandaki round-trip fixture does not exist on a fresh clone** — the gate must ship self-contained fixtures under `shared/src/fhir/__fixtures__/`.
4. **`formId` does not exist at parse level** — it is constructed at the server as `${category}:${basename}` (`D:\cht-ui-builder\server\src\routes\forms.ts:22`, where `parseFormId` does `rest.join(':')` so a basename may contain `:`). The sidecar key codec must own that boundary, must be **injective and canonical** (orphan matching depends on it — see Section 4.2 / 4.5), and must escape delimiter collisions.
5. **The "zero SNOMED" guard is a `node --test` assertion, NOT a CI assertion — there is no CI in this repo** (no `.github/`, `.gitlab-ci`, `.circleci`, or any workflow file exists). The guard is only real if it runs unattended, so this slice **adds a minimal CI workflow** that runs build + test + lint on push (Section 4.12). The guard also scans both the parsed object AND the raw file bytes, and also flags SNOMED provenance hiding in free-text `aliases`/cross-map fields (Section 4.7 / 4.9), or it is theater.
6. **The proposal conflates `source` (where a code came from) with `confirmedBy` (has a human blessed it), and has no representation for "Skip."** The schema adds a `status` (`suggested | confirmed | skipped | orphaned`) before freezing `schemaVersion: 1`, or V1 pays a migration tax.

**Licensing reality the slice ships:** this slice ships LOINC and ICD-11 content in `cht-mch-v1.json`. SNOMED-off-by-default is enforced; LOINC and ICD-11 attribution obligations are also satisfied with a committed NOTICE file (Section 4.7) — all three corpora land in this commit, not just SNOMED.

None of these block the slice; they are the acceptance bar.

## 3. Round-trip safety contract (what THIS slice touches and what it must NOT break)

**The only file this feature ever writes is `fhir-mapping.json` at project root.** In the MVP slice there is no writer at all (no server route) — the slice ships a pure deterministic `serialize()` function plus tests. The contract the module's API guarantees, to be inherited by the V1 route:

1. **Never touch any XLSX, `properties.json`, or `base_settings.json` byte.** No mapping metadata in `SurveyRow.extras`, `ChoiceRow.extras`, `FormSettings.extras`, or `properties.json`. (Dealbreaker for Developer + QA: a single non-sidecar byte changing = hard reject.)
2. **Never mutate `tasks.js`, `contact-summary.templated.js`, or `place-types.json`.** Codes live exclusively in `fhir-mapping.json`.
3. **Reorder or drop nothing the tool does not own.** Unknown JSON fields (top-level AND per-entry) round-trip verbatim, written back in sorted position. Preservation copies keys **unconditionally** — a future field whose value is `null`, `0`, `false`, or `""` survives; `serialize` never introduces an `undefined` value (which `JSON.stringify` would silently drop). (XLSForm-extras rule, restated and hardened for the sidecar.)
4. **Idempotence, not raw no-op.** The guarantee is `serialize(parse(serialize(x))) === serialize(parse(x))` (the serializer is a fixpoint), and `serialize(parse(bytes)) === bytes` **only when `bytes` were produced by this serializer**. A foreign-formatted sidecar (CRLF, 4-space indent, unsorted keys, `\uXXXX` string escapes, non-canonical number literals such as `0.10`/`1.0`/`1e3`/integers `> 2^53`) is **canonicalized exactly once** on first save — this is intentional, tested (4.10 #1/#9/#10), and documented. After that first save the file is a fixpoint. When the V1 route lands, it MUST read existing bytes, compare to new bytes, return early if equal, and use the atomic tmp+rename pattern from `D:\cht-ui-builder\server\src\routes\hierarchy.ts:45-49` — NOT the non-atomic `fs.writeFile` that `forms.ts` uses for `properties.json`. The route's read-compare-before-write suppresses spurious writes **only** for files already canonical; the one-time canonicalization of a foreign file is expected behavior, not a bug. (Flagged here so the route author neither copies the weaker write pattern nor treats the first rewrite as a defect.)
5. **Encoding is UTF-8 without BOM, LF line endings.** Read and write as `'utf8'` matching the existing BOM-free writes in `hierarchy.ts`/`state.ts`. Windows tooling can introduce a BOM; the serializer/route MUST NOT. Non-ASCII `display` values are emitted as literal UTF-8 (a source file using `\uXXXX` escapes is canonicalized to literal UTF-8 once per caveat 4).
6. **Never silently drop or false-orphan a binding.** When a question is renamed/deleted, `reconcile()` relocates its mapping to `orphans[]` with enough payload to reconstruct the human-facing card (original key, full code object, reason). **Orphan matching is by string set-membership of live keys against the encoded keys in `questionMappings`.** This depends on the codec being injective + canonical (Section 4.2) AND on the caller producing `liveQuestionKeys` via the **same codec** (`encodeQuestionKey` / `encodeChoiceKey`) — **string concatenation of `formId + '/' + name` is forbidden**, because a name legally containing `/` or `%` would then fail to byte-match the escaped on-disk key and a confirmed, still-live binding would be silently relocated to `orphans[]` (a false-orphan data-loss bug). This requirement binds both the data layer (4.5) and the V1 route (Section 6). The codec operates on already-URL-decoded `formId`/`name` values (post `decodeURIComponent`, which the form route applies at `forms.ts:163`), so the sidecar's percent-encoding is the single canonical on-disk encoding layer — never run it on raw URL path segments.
7. **`orphans[]` order is deterministic.** `reconcile()` sorts the resulting `orphans[]` by `originalKey`, then `system`, then `code` as tiebreaks, so two reconcile runs over the same logical state but different `questionMappings` insertion orders produce byte-identical output. `sortDeep` (the serializer) canonicalizes object **keys only** and MUST NOT reorder arrays (array order can be semantically meaningful); array canonicalization is the responsibility of the producing function (`reconcile`), not the serializer.
8. **Never write a mapping the user didn't confirm.** Starter-pack pre-fills land with `confirmedBy: null` / `status: "suggested"`; they count as "pending review," never "mapped/confirmed." A later starter-pack re-apply MUST NOT overwrite a row whose `confirmedBy` is non-null (tested in MVP via `applyStarterPack` pure function).

**No non-determinism in the serialize path:** no `Date.now()`, no wall-clock, no env-dependent output, no unsorted `Object` iteration, no array reordering. The `appliedAt` timestamp is supplied by the caller (V1 route), never generated inside `serialize`/`parse`/`applyStarterPack`.

**Number/string canonicalization is an accepted, frozen behavior (not a leak):** because `parse` uses `JSON.parse`, numeric literals are normalized (`0.10`→`0.1`, `1.0`→`1`, `1e3`→`1000`, `>2^53` lose precision) and `\uXXXX` escapes become literal UTF-8. The chosen contract is **(a): numbers and strings are canonicalized**, downgrading the guarantee from byte-equal-to-arbitrary-input to idempotence-after-first-save. This is tested explicitly (4.10 #9/#10) so it is an intentional frozen contract, not a surprise. (Option (b) — preserving raw numeric literals as strings in `extras` — is explicitly rejected for MVP to keep the codec simple; revisit only if a real config is found to depend on literal number formatting.)

### 4.2 `shared/src/fhir/key.ts` (new) — key codec (Developer must-have #5; injective + canonical)
**Contains:** `encodeQuestionKey(formId: string, name: string): string`, `decodeQuestionKey(key): { formId; name }`, `encodeChoiceKey(formId, list_name, name): string`, `decodeChoiceKey(key): { formId; list_name; name }`. Canonical question key = `${encSeg(formId)}/${encSeg(name)}` (e.g. `app:pregnancy/lmp_date`); choice key = `${encSeg(formId)}/${encSeg(list_name)}/${encSeg(name)}`, where `encSeg` percent-encodes `%` → `%25` and `/` → `%2F` (in that order) **per segment**. **`:` inside `formId` is intentionally NOT escaped** (only `/` and `%` are), because `parseFormId` (`forms.ts:31`) does `rest.join(':')` so a basename may legally contain `:`. `decode` splits on the **unescaped** `/` separator (the only `/` characters present are separators, since all in-segment `/` were percent-encoded), then percent-decodes each segment. A documentation comment states the layer boundary: **`formId` is constructed at the server as `${category}:${basename}` (`D:\cht-ui-builder\server\src\routes\forms.ts:22`) and passed in already URL-decoded (the form route does `decodeURIComponent(req.params.id)` at `forms.ts:163`); the parser never produces `formId`, and the codec runs on post-`decodeURIComponent` values so the sidecar's percent-encoding is the single canonical on-disk encoding layer.**
**Acceptance:** colocated `key.test.ts` proves, frozen as the codec compatibility contract:
- **Round-trip** `decode(encode(x)) === x` for the question key with: a plain key, a basename containing `:`, a name containing `/`, a name containing `%`, and an empty-string segment.
- **Round-trip** the full 3-segment **choice** key with delimiters in every position: `/` in `list_name`, `/` in `name`, `%` in `list_name`, `:` in the `formId` segment combined with `/` in `name`, and an empty-string segment — asserting the decoder yields exactly the original `{formId, list_name, name}` triple (the multi-segment ambiguity case the proposal never tested; the format is frozen now because `choiceMappings` is reserved `{}` and V1 inherits it unmigrated).
- **Injectivity / canonicality:** `encodeQuestionKey('app:preg', 'a/b') !== encodeQuestionKey('app:preg/a', 'b')`, and both decode to their correct distinct tuples (proves no two distinct tuples collide to one string — the property orphan matching actually depends on, which a bare round-trip test does NOT prove).

### 4.3 `shared/src/fhir/parse.ts` (new)
**Contains:** `parseFhirMapping(source: string): FhirMapping`. Parses the JSON, validates structure, and routes every key it doesn't model into `extras` (top-level) or per-entry `extras`. The `extras` routing copies keys **unconditionally** (`Object.prototype.hasOwnProperty` / spread, never a truthiness check) so a future field valued `null`/`0`/`false`/`""` is preserved, not dropped. Throws a typed `FhirMappingError` (defined here or in `types.ts`) — NOT a raw `SyntaxError` — on: missing/non-numeric `schemaVersion`, non-object `questionMappings`, an entry whose `code`/`system`/`display` is the wrong type. Required-vs-optional enforcement: `code`, `system`, `display`, `source`, `dictionaryVersion`, `status`, `confirmedBy`, `confirmedAt` are required on each `QuestionMapping` (MOH reviewer must-have — provenance is mandatory, not optional).
**Acceptance:** `parseFhirMapping('{}')` throws `FhirMappingError` with a clear message; a malformed `code: 123` throws typed, not raw; a valid sidecar parses to the expected object; unknown top-level + per-entry keys land in their respective `extras`, including keys valued `null`/`0`/`false`/`""`.

### 4.4 `shared/src/fhir/serialize.ts` (new) — deterministic serializer (Developer/QA/Designer must-have)
**Contains:** `serializeFhirMapping(m: FhirMapping): string`. Implements a recursive **sorted-key** serialization via a `sortDeep()` that returns a new object with **object keys** inserted in sorted order — **`sortDeep` MUST NOT reorder arrays** (array order is the producer's responsibility; see Section 3 item 7). Re-merges `extras` so unknown fields are written in sorted position, copying **unconditionally** and never introducing an `undefined`-valued key. Then `JSON.stringify(sorted, null, 2)`, normalizes to **LF** line endings, and appends exactly one trailing `\n`. Output is UTF-8 without BOM. Pure: no clock, no env reads, no array reordering. Reference the deterministic-serialization discipline in `D:\cht-ui-builder\shared\src\xlsform\serialize.ts`.
**Acceptance:**
- **Idempotence:** `serializeFhirMapping(parseFhirMapping(serializeFhirMapping(parseFhirMapping(s)))) === serializeFhirMapping(parseFhirMapping(s))` for the committed fixture (the serializer is a fixpoint).
- **No-op on own output:** for the committed (already-canonical) fixture, `serializeFhirMapping(parseFhirMapping(fixtureBytes)) === fixtureBytes`.
- **One-time canonicalization (boundary pinned):** for a deliberately NON-canonical input (CRLF + 4-space indent + unsorted keys), `serialize(parse(it)) !== it` BUT `serialize(parse(serialize(parse(it)))) === serialize(parse(it))` — proving the first rewrite is intentional and the result is thereafter stable.
- **Order-independent determinism:** two `FhirMapping` objects built with keys inserted in different orders serialize to identical bytes.
- output ends in exactly one `\n`; output contains no `\r`; output contains no BOM.

### 4.5 `shared/src/fhir/reconcile.ts` (new) — pure orphan reconciliation (Developer must-have #4, MOH/QA must-have)
**Contains:** `reconcileFhirMapping(mapping: FhirMapping, liveQuestionKeys: string[]): FhirMapping`. Pure, side-effect-free. For each entry in `questionMappings` whose key is NOT in `liveQuestionKeys`, move it into `orphans[]` as an `OrphanEntry { originalKey, code, system, display, source, dictionaryVersion, confirmedBy, confirmedAt, reason }` where `reason` is `'renamed-or-deleted'` (MVP cannot distinguish rename from delete without diff context; document that V1's route may refine `reason` to `'renamed' | 'deleted' | 'list-changed'`). Entries whose key IS live are kept untouched (including `confirmedBy`). The resulting `orphans[]` is **sorted deterministically by `originalKey`, then `system`, then `code`** (Section 3 item 7) so the serialized output is byte-stable regardless of input `Record` insertion order. Never mutates the input; returns a new object.
**Caller contract (binds the V1 route too):** `liveQuestionKeys` MUST be produced by calling `encodeQuestionKey(formId, row.name)` / `encodeChoiceKey(...)` from this same codec module — **never by string concatenation** — or a name containing `/`/`%` will false-orphan a live confirmed binding (Section 3 item 6). Document this in the function's doc comment.
**Acceptance:** `reconcile.test.ts`:
- Given a mapping with `app:pregnancy/lmp_date` confirmed and live keys NOT containing it, the result has zero `questionMappings` for that key and exactly one `orphans[]` entry preserving the full code + `confirmedBy`. A confirmed binding is never dropped.
- Given the key still live, the entry is byte-stable after reconcile→serialize.
- **Deterministic orphan ordering:** run `reconcile` twice over inputs whose `questionMappings` were inserted in **opposite** orders and produce multiple orphans; assert byte-identical serialized output **including the `orphans[]` ordering** (this is the array-ordering non-determinism the proposal's key-only determinism test could not catch).
- **False-orphan guard:** a live question whose `name` contains `/` (live key produced via `encodeQuestionKey`) is **retained, not orphaned**.

## 5. Data shapes (VERIFIED stable-key shape — corrects the proposal)

**Layer-boundary note (grounding):** `formId` is NOT returned by `parseXlsForm()`. It is constructed at the server as `${category}:${basename}` (`forms.ts:22`); `parseFormId` does `rest.join(':')` (`forms.ts:31`) so a basename may legally contain `:`. `SurveyRow.rowId` (`r_N`) and `ChoiceRow.rowId` (`c_N`) are sequential counters — NOT stable across re-parse — and are correctly rejected as keys. The stable identifiers are `SurveyRow.name` (questions) and `(ChoiceRow.list_name, ChoiceRow.name)` (choices); the sidecar wraps these with the routing `formId` via the injective/canonical key codec in 4.2. The form route URL-decodes the id (`decodeURIComponent`, `forms.ts:163`) before it reaches the codec, so the codec's percent-encoding is the single on-disk encoding layer.

### TypeScript type (`shared/src/fhir/types.ts`)
```ts
export type MappingStatus = 'suggested' | 'confirmed' | 'skipped' | 'orphaned';
// 'online:${string}' is RESERVED-BUT-UNREACHABLE in MVP: no network producer
// ships in this slice. Emitting it requires the V1 contract-test gate
// (recorded fixtures + circuit breaker) before any fetch may produce it.
export type MappingSource = 'starter-pack' | 'manual' | `online:${string}`;

export interface QuestionMapping {
  code: string;                 // required
  system: string;               // required, e.g. 'http://loinc.org'
  display: string;              // required, human-readable clinical name
  source: MappingSource;        // required: where the code came from
  dictionaryVersion: string;    // required, e.g. 'LOINC-2.82'
  status: MappingStatus;        // required: derivable workflow state
  confirmedBy: string | null;   // required: reviewer identity, null = not blessed
  confirmedAt: string | null;   // required: ISO timestamp, null = not blessed
  confidence?: number;          // reserved for V1 suggest-a-code (canonicalized number; see Section 3)
  clinicalReview?: { reviewer: string; reviewedAt: string }; // reserved V1
  extras: Record<string, unknown>; // unknown per-entry keys, preserved verbatim+sorted (incl. null/0/false/"")
}

export interface OrphanEntry {
  originalKey: string;          // e.g. 'app:pregnancy/lmp_date' (codec-encoded)
  code: string;
  system: string;
  display: string;
  source: MappingSource;
  dictionaryVersion: string;
  confirmedBy: string | null;
  confirmedAt: string | null;
  reason: 'renamed-or-deleted'; // V1 may refine to renamed|deleted|list-changed
}

export interface StarterPackRef { id: string; appliedAt: string; }

export interface FhirMapping {
  schemaVersion: 1;
  starterPack: StarterPackRef | null;
  questionMappings: Record<string, QuestionMapping>; // key = encodeQuestionKey
  choiceMappings: Record<string, ChoiceMapping>;     // reserved {} for V1
  orphans: OrphanEntry[];                             // sorted by reconcile: originalKey, system, code
  extras: Record<string, unknown>;                    // unknown top-level keys, preserved verbatim (incl. null/0/false/"")
}
```
`ChoiceMapping` mirrors `QuestionMapping` and is reserved (`choiceMappings: {}`) so V1's `(formId, list_name, name)` 3-tuple needs no migration; its key format is already frozen and tested in 4.2.

User decision, 2026-06-05. The per-column picker is **two-step**: (1) choose the code system / dictionary, (2) search within it by clinical name and pick the code. Selectable dictionaries are the free, vendored ones: **LOINC, ICD-10, ICD-11, CIEL** (ICD-10 included by user decision — also free from WHO). **SNOMED is never in the selectable set** (Decision 1); the zero-SNOMED guard applies across every vendored dictionary.

- **No sidecar schema change** — each entry already carries `system` + `code` + `display` + `dictionaryVersion`; the chosen dictionary is recorded in `system`. Starter-pack pre-fills still suggest one default binding per row (the obvious LOINC/ICD code), and the user can switch dictionary and re-pick.
- **The vendored pack must carry MULTIPLE code systems**, not just LOINC. The pack format gains an enumerable "available dictionaries" list the picker reads; `build-terminology-pack.mjs` (Decision 2) snapshots each free system into the committed pack. Adding ICD-10 later is a data add, not a code change, because the picker is dictionary-agnostic.

**Unchanged:** the MVP `shared/` slice (types, key codec, parse/serialize, reconcile, starter pack, tests, CI) is identical under all of these UI decisions — the developer can start it now; Decisions 3–4 only shape the later V1 UI.


### Decision 4 clarification — mixing systems within one form; question- vs choice-level

The dictionary is chosen **per mapping, not per form**, so a single form freely mixes code systems. Example in `app:pregnancy`: `lmp_date` → **LOINC** 8665-2 (an observation / "what was measured"), while a `mother_conditions` select maps each disease to an **ICD** code (a diagnosis). This is the canonical split — LOINC codes observations, ICD codes diagnoses/conditions — and maps directly to FHIR (`Observation.code` = LOINC, `Condition.code` = ICD), which is what the V2 Questionnaire export consumes.

This means the workbench supports **two granularities**, both already in the plan (no schema change):
- **Question-level** mapping (the column itself) — keyed by `(formId, name)`. LOINC fits most observations.
- **Choice-level** mapping (each option of a `select_one`/`select_multiple`) — keyed by `(formId, list_name, choice.name)`, stored in the sidecar's `choiceMappings` block. ICD fits disease/condition option lists. In the workbench, a `select_*` row **expands to its options**, each with its own dictionary + code picker.

So "map `lmp_date` with LOINC, map each mother-disease option with ICD, in the same pregnancy form" is exactly the intended flow.
