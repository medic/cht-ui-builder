# Plan: Calculation / formula builder — value-producing `calculation` column

**Version:** v0.2 — 2026-06-15 · **Status:** PLANNER-LOCKED, developer-ready.
**Written to:** `d:\cht-ui-builder\docs\plans\calculation-builder.md` (full plan; this is the summary).

> All line anchors below were re-pinned against current HEAD (commit `2770f2a`). Because `FormEditor.tsx` and `conditionReducer.ts` are actively churning on the parallel condition-builder branch, **anchors are paired with the stable symbol name — grep the symbol if the number has drifted.** All corpus numbers were measured directly against `server/templates/cht-default/forms/app/*.xlsx` via compiled `shared/dist` on 2026-06-15 (see §6).

This is a *separate* feature from `docs/plans/condition-builder.md` (v0.3, boolean columns). `calculation` produces a VALUE, not a yes/no, and does not fit the AND/OR clause model. The plan **extends** the existing `shared/src/xlsform/calculationBuilder.ts` + `client/src/ui/CalculationBuilder.tsx`; it does not reinvent them, does not add a parallel parser, and does not widen `parseRelevant`'s `ParsedExpression` return type.

> **Sequencing (planner, 2026-06-15):** CB v0.3 ships FIRST (already handed to the developer); this calc plan starts with Tier 0 afterward. Opportunistic free win: the double-door one-liner (drop `calculation` from the boolean builder COLUMN_OPTIONS + a hydrateColumn early-return for non-boolean columns) is a ~2-line change the dev can fold into CB v0.3, since v0.3 already edits that exact column dropdown -- it kills the worst corruption immediately; the rest of Tier 0 follows later.

## Feasibility verdict
Feasible, and the skeleton already exists. Four round-trip facts (empirically verified against the cht-default forms and compiled `shared/dist`) drive the plan. Facts 1–3 were in v0.1; fact 4 (truncation/data-loss) is new and is a *distinct* failure class:

1. **`parseCalculation` has NO top-level self-check.** `if(${a}=1,2,3)` re-serializes to `if(${a}=1, 2, 3)` on a no-op open/save — silent corruption — yet stays `shape:'decision_table'`. `peelIfChain` (calculationBuilder.ts:56-71) only self-checks each *condition* via `parseRelevant`; the if-chain comma/glue scaffolding is reassembled with zero verification. **17 of the 55 distinct cht-default if-chains are already unstable this way** (§6).
2. **Empty-cell `''` resurrection.** `parseCalculation('')` → `otherwise:"''"`; `serializeCalculation` returns the literal two-char string `''`, not the JS empty string. `setExtra` only deletes when `value === ''` (FormEditor.tsx:743-749, delete at line 746), so opening+saving an absent calc cell resurrects it with a stray `''`.
3. **Non-if cells are mislabeled but happen to round-trip.** Real cells (`../inputs/contact/_id`, `difference-in-months( ${dob}, today() )`, bare `${field}`) parse to `shape:'decision_table', rules:0` with the whole expr in `otherwise`; stable only by accident of the `rules:0` branch (serializeCalculation line 45). **205 of 258 distinct cells are `rules:0` today** (§6).
4. **Trailing-text TRUNCATION (data loss, not reformat).** `readArgList` (calculationBuilder.ts:95-99) returns at the first balanced close paren and discards the remainder. So `if(${a}=1,2,3) + 5` parses to `shape:'decision_table'` and serializes to `if(${a}=1, 2, 3)` — **the trailing ` + 5` is silently DROPPED.** Same for `if(...) div 12`. The §3.1 self-check defends against this (the truncated re-serialize ≠ the original, so it demotes to raw), but it is a different bug from facts 1–3 and MUST be proven in Bucket B (§6), not assumed.

**The gate (double-door bug, verified):** `calculation` is in the `ConditionColumn` type (conditionReducer.ts:69-73) AND `COLUMN_OPTIONS` (FormEditor.tsx:1154-1159, the `calculation` entry at line 1156), selectable from the condition builder's column `<select>` (FormEditor.tsx:1626-1638, driven by `onPickColumn`). On select, `set-column` → `hydrateColumn` (conditionReducer.ts:518-522) runs `parseRelevantGrouped` on it **unconditionally — parsing a value-producing expression as a boolean AND/OR chain**, silently corrupting it (grounding `risksForPlan`). The dedicated, correct path is `ExpressionField` → `CalculationBuilder` via the `supportsCalculation` guard (FormEditor.tsx:1035, mount 1083-1088).

## Scope — measured against the corpus (re-ranked by frequency)
The cht-default corpus has **258 distinct calc cells** (473 occurrences across 11 forms). Distribution (§6): **55 if-chains** · **202 single-value (non-if)** · **1 canonical age template** · **0 flat arithmetic** · **0 BMI**. Of the 202 single-value cells: 91 bare `${field}`, 63 xpath paths (`../inputs/...`), 9 literals, and **39 contain a function call** (jr:choice-name, format-date-time, decimal-date-time, concat, …) that stay raw-fallback. So the genuine, cheap win is **Tier 0 + the single-value editor** (≈163 cleanly-buildable single-value cells + de-corrupting the 55 if-chains). Flat arithmetic and the BMI marquee from v0.1 are **NOT in the corpus** and are demoted; the age recipe has **exactly 1 occurrence** and rides opportunistically.

**Tier 0 — Gate + round-trip safety (ship first, no new visible shapes):**
(1) remove `'calculation'` from `COLUMN_OPTIONS` and the `ConditionColumn` type; add a **defensive early-return in `hydrateColumn`** for any column outside the boolean set (cheap insurance against a future/persisted caller forcing `'calculation'` back in);
(2) add a **top-level self-check to `parseCalculation` that runs for EVERY non-raw shape** (mirror relevantParser.ts:184-186);
(3) fix the empty-cell `''` resurrection — collapse to JS `''` **only for the genuinely-empty source** (§3.3);
(4) reclassify `rules:0` cells to `shape:'single'` (preserves the accidental stability deliberately).

**Tier 1 — Single-value editor + mode shell + age template (core, corpus-grounded):**
explicit top-level mode selector (a11y radio/tablist: *Single value · If-then table · Common calculation · Raw*); a **single-value mode** (bare `${field}` picker / xpath / literal with visible auto-quote) — this covers the largest measured slice; templates gallery FIRST on an empty cell, currently just **Age from DOB** (the one recipe with corpus support); typed output affordance (literal / number / field-ref, visible auto-quote) replacing the bare `<input placeholder="'yes' or 5">` at CalculationBuilder.tsx:116-120/132-136; plain-language `Result: …` readback above the collapsible raw `<pre>` (CalculationBuilder.tsx:145-148). **Also in Tier 1 (§3.5): replace the local `serializeRelevantStub`** (CalculationBuilder.tsx:208-229) with the real `serializeRelevant` import.

**Tier 2 — Flat N-ary arithmetic (opportunistic, behind real-form discovery):**
`+ − × ÷` → `+ - * div` with one paren level (e.g. BMI `${weight} div (${height} * ${height})`). **Cut from MVP-core** because the corpus contains zero such cells; build only if/when a real project surfaces them. Until then these cells ride the raw fallback safely.

**Out of scope (raw-fallback in MVP, byte-stable):** concat, int()/number()/string() casts, coalesce `or` (XForms string-coalesce — must NEVER share the boolean `or` path), jr:choice-name, format-date-time, decimal-date-time arithmetic, aggregates over repeats, date diffs beyond the age recipe, 3-level nesting, pulldata, regex, grouped `(A and B) or C` inside `if()`, bidirectional field-delete invalidation.

## The four locked decisions
1. **UX model:** explicit top-level mode selector + templates-first gallery; progressive disclosure (single value never shows the decision grid). Each mode is a thin UI over ONE recognizer union — not a second grammar. Scope is ranked by the measured corpus, not by aspirational examples.
2. **Grammar boundary:** buildable = decision table (shipped) + single value + age template (Tier 1); flat N-ary arithmetic is Tier 2/opportunistic. Everything else is raw-fallback with proven byte-stability. Each shape ships with its own self-check + Bucket A/B/C coverage.
3. **`if()` boolean test:** reuses the existing `parseRelevant`/`serializeRelevant` (calculationBuilder.ts:17,50,67; CalculationBuilder.tsx:16) — no second boolean grammar; `parseRelevant`'s return type is NOT widened. The local `serializeRelevantStub` is **deleted** in favor of the shared `serializeRelevant` (it already drops `age`/`date_offset`, so if()-condition spelling for those kinds does not survive round-trip today — §3.5).
4. **Round-trip contract:** persist ONLY `row.extras['calculation']` as a string; mandatory top-level self-check on every non-raw shape; raw-fallback sacred and byte-identical; **a present cell is NEVER turned into a deleted one** (§3.3).

## Round-trip safety contract (highlights)
- **§3.1 — top-level self-check, ALL non-raw shapes.** `serializeCalculation(parseCalculation(x)) === x.trim()` must hold for every result whose `shape !== 'raw'` — `decision_table`, `single`, and (later) `arithmetic` alike. If it fails, demote to `shape:'raw'` with `raw` = the original trimmed text and serialize verbatim. **This must NOT be skipped for `'single'` "because it's trivially stable" — it is the only thing that rescues the §3.3 deletion hazard and the fact-4 truncation case.** The self-check and §3.3 share the SAME `serializeCalculation`, so the ordering is: parse → self-check (via that serializer) → on mismatch, raw.
- **§3.3 — empty-cell collapse, genuinely-empty ONLY.** `serializeCalculation` collapses `otherwise === "''"` to JS `''` (length 0, so `setExtra` deletes cleanly) **only when `parsed.raw.trim() === ''`** (the source cell was truly blank). A **non-empty cell whose canonical serialize would be length-0** — e.g. a deliberate literal `''` calculation that was present in the source xlsx — MUST route through §3.1 to `shape:'raw'` and be preserved verbatim. **A present column is never deleted.** (The cht-default corpus has 0 such cells today — §6 — but the contract must hold for real configs that do.)
- **§3.4 — one discriminated recognizer; no partial-parse-and-drop.** Reject the fact-4 truncation class explicitly: after peeling an if-chain, if any trailing text remains beyond the closing paren, the whole expression is not a clean decision table → self-check catches it → raw.
- **§3.5 — if() reuses the frozen condition grammar.** No widening of `ParsedExpression`; no third copy of serialization. **Delete `serializeRelevantStub`** and import the real `serializeRelevant` (RelevantRuleBuilder.tsx:12 already imports it from `@cht-ui/shared` with no dependency cycle, so the "avoid a dependency cycle" comment at CalculationBuilder.tsx:209-210 is stale). The stub's switch only handles comparison/selected/answered/raw and silently drops `age`/`date_offset`, so an `if()` condition spelled with an age or date-offset rule does not round-trip today; the import fixes it.
- **§3.6 — double-door removed AND guarded.** Primary fix: remove `'calculation'` from the `ConditionColumn` type and `COLUMN_OPTIONS` (closes the runtime path). Secondary insurance: a one-line early-return in `hydrateColumn` for any column not in the boolean set. Regression tests assert both the type/`COLUMN_OPTIONS` shape AND that `hydrateColumn` fed a forced `'calculation'` value does **not** produce committed AND/OR clauses.
- **§3.7 — DecisionsView is a real consumer.** `DecisionsView.tsx:242-243` reads `parsed.shape === 'decision_table' && parsed.rules.length > 0`. Widening the union is additive for that `===` comparison (typechecks), but the view must be re-checked: after the `rules:0`→`single` reclassification and the fact-1 raw-flip, the **17 unstable if-chains will demote to raw and disappear from the Decisions sign-off table.** See the flip-policy below.

## Regression-flip policy (Lorena / MOH-reviewer surfaces)
The Tier-0 self-check correctly demotes the **17 distinct if-chains** (of 55) that re-serialize to a different byte string today. Those 17 currently render as structured tables in both `CalculationBuilder` and `DecisionsView`; under the self-check they flip to a raw textarea and drop out of the read-only Decisions view (which gates on `decision_table` + `rules>0`). **Documented policy:** accept the flip (it replaces silent corruption with honest raw) and note that DecisionsView coverage drops for exactly those cells until a user re-saves one through the builder, which canonicalizes spacing and restores the structured table. **No auto-normalize-on-save** in MVP (it would mutate cells the UI doesn't own). A Bucket-C test pins the exact set of 17 so the count cannot silently grow.

5. **`serializeRelevantStub` is deleted, not patched** — the "dependency cycle" comment is stale (RelevantRuleBuilder already imports `serializeRelevant` cleanly), and patching would still risk drift from the canonical serializer.
